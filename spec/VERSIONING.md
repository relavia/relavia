# 统一节点模型 · 版本化规则

- 状态：已评审冻结（随统一节点模型 v1 于 2026-11-12 评审冻结）
- 依据：方案书 5.2「模型版本化，变更走 RFC 流程」与 10.3 决策机制（协议矩阵增减、统一模型大版本等事项走 RFC：公开提案 + 讨论期 + 维护者裁定并记录理由）

## 1. 版本字段

- 四个模型（Node、Group、Source、Subscription）的每个文档都必须携带顶层字段 `schemaVersion`，字符串格式 `大版本.小版本`，如 `"1.0"`。
- 当前发布的 schema 文件对应大版本 1；其 `schemaVersion` 定义为模式 `^1\.[0-9]+$`，即 v1 系列 schema 接受同一大版本内任意小版本文档。这是下文「同大版本向前兼容」在校验层的落点：消费者不得因小版本号高于自身认识而拒绝文档，只能忽略不认识的可选字段。
- schema 文件本身的变更以 Git 历史与发布说明为准；文件名 `unified-node-model.schema.json` 不带版本号，大版本升版时新旧两份 schema 在仓库中共存一整个大版本周期（见第 4 节）。

## 2. 版本号语义

- **小版本（minor）**：向后兼容的扩展，包括：
  - 新增可选字段（任何层级）；
  - 新增模型种类；
  - 放宽约束（如扩大数值范围、枚举新增取值属有条件小版本，见第 3 节第 4 条）；
  - 新增协议分支（须先过方案书 4.3 的矩阵流程，即互通测试后进矩阵，再进模型）。
- **大版本（major）**：任何破坏兼容的变更，包括：
  - 删除或重命名字段；
  - 改变字段类型或语义；
  - 可选字段改为必填、必填约束收紧；
  - 删除协议分支或枚举取值；
  - 判别联合结构（按 `protocol` 分支）本身的组织方式变更。

## 3. 向后兼容原则

1. 同一大版本内，旧消费者必须能读取新文档：忽略未知可选字段后语义不变。
2. 同一大版本内，新消费者必须能读取旧文档：新增字段一律可选且有合理缺省语义，不得要求旧文档补字段才能解析。
3. 枚举与协议的新增取值对旧消费者是「不认识」而非「非法」：旧消费者应将其标记为不支持并保留原始数据（与方案书 5.3「禁止静默失败、UI 灰化不支持项」一致），不得丢弃整个文档。
4. 枚举新增取值虽属小版本，但因影响互通面，须在发布说明中显著标注；删除取值永远走大版本。
5. 凭据类字段（密码、密钥、订阅 URL）永不改名、永不换语义，即使大版本变更也应提供自动迁移（第 4 节），因为它们没有「让用户重新填一遍」的退路。

## 4. 大版本变更流程（RFC）

1. **提案**：在仓库以 RFC 文档形式提交，写明变更动机、受影响字段清单、对既有文档的破坏面与迁移方案；
2. **讨论期**：公开讨论，维护者收集解析器、来源插件、内核适配层三方的受影响评估（模型的所有生产方与消费方都必须表态，缺一方不得进入裁定）；
3. **裁定**：由维护者裁定并记录理由（10.3）；裁定不通过则提案归档，不留口头结论；
4. **双读期**：新大版本发布后，消费者须至少在一个大版本周期内同时读得懂新旧两版文档；生产方（解析器、插件）在双读期内只写新版；
5. **迁移**：随新大版本提供旧文档自动迁移工具与迁移自测样本；凭据类字段迁移后须逐字段可核对；
6. **旧版退役**：双读期结束、迁移工具覆盖的样本全过后，旧大版本 schema 转入仓库归档目录，只读不再修订（安全问题除外，安全修订须公示）。

## 5. 小版本变更流程

小版本不走完整 RFC，但须：维护者评审合并、发布说明逐条列明新增字段/取值、示例集与校验用例同步更新（新增字段至少补一个正例；约束类调整补反例），且 `tests/validate.py` 全过后才可发布。

## 6. 冻结与状态标注

- 本规则与模型 v1 目前同为**候选**状态；在评审冻结前，允许在本文件与 README 中以修订形式调整，调整须留 Git 记录；
- 冻结后，本文件自身的规则变更按「大版本变更流程」同等级处理（规则管规则的部分从严）；
- 任何对外文档引用本模型时必须标注其状态（候选 / 已冻结）与 `schemaVersion` 大版本，不得以候选版本冒充定版。
