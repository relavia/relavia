## 0. 口径总表（本方案锁定的十条）

以下十条是本方案书与用户此前讨论中已确认的结论，全文各章不得与之冲突；如需变更，须先修订本节并注明变更原因。

1. **产品形态**：本项目只做客户端软件，不做节点服务商。软件开源发布，空壳分发，不内置任何写死的节点地址。
2. **盈利模式**：永久非盈利。无会员、无付费功能、无广告、无流量转售、无捐赠换权益。
3. **兼容策略**：以「全主流协议兼容」为目标，对外只承诺公开的兼容矩阵（第 4 章），不承诺字面意义上的「所有协议」；矩阵外协议明确标注不支持或规划中。
4. **自研路线**：外壳（UI、统一配置模型、订阅解析、来源插件）第一天起完全自研；内核采用可插拔适配层，第一版挂接成熟开源内核，之后按协议逐个自研替换。自研是终点，不是起点（理由见 2.2）。
5. **语言与技术栈**：内核与核心层使用 Go；客户端 UI 层按平台选型但必须与核心层解耦（第 5 章）。不采用 Rust 作为主语言，原因是贡献者门槛与生态复用。
6. **公共节点来源**：只接入有明确授权依据的公开来源。首个且一期唯一的官方公共源为日本筑波大学 VPN Gate 学术实验项目（其官方明确提供 CSV 列表供第三方制作客户端）。未经授权的共享、泄露、扫描所得节点一律禁止进入任何官方来源（第 7 章）。
7. **隐私底线**：无账号系统、无中心服务器、无遥测、无第三方统计或广告 SDK。客户端自身不记录用户访问日志；但必须如实告知用户：所使用的第三方节点（尤其志愿者节点）可能记录连接日志，客户端无法替节点作无日志承诺（第 9 章）。
8. **许可证**：主仓库采用 GPLv3（防闭源打包转售，见第 10 章）；项目名称与 Logo 不随代码开源，保留商标权以防冒牌客户端。
9. **平台顺序**：Windows + Android 先行，macOS 与 Linux 次之，iOS 最后单独立项评估（第 12 章）。
10. **运营成本模型**：架构层面做到零服务器成本；仅保留域名、代码签名、开发者账号等小额刚性支出，靠公开透明的捐赠覆盖，账目公开（第 11 章）。

**明确不做的事（负面清单）**

- 不运营、不托管、不出售任何节点或订阅服务。
- 不抓取、不聚合未经授权的第三方节点（包括但不限于泄露的订阅、扫描出的开放代理、他人账号）。
- 不内置后门、不做流量劫持、不做任何形式的用户行为上报。
- 不承诺绕过任何特定国家或地区的法律法规；软件定位为通用网络代理工具，用户须自行确保其使用符合所在地法律。
- 一期不做志愿者中继网络（用户贡献带宽当节点）；该方向列为远期独立评估项（第 13 章风险 R-09），客户端成熟前不碰。

## 1. 项目概述

### 1.1 背景与动机

当前主流代理协议碎片化严重：不同协议、不同订阅格式、不同客户端之间互不兼容，用户被迫在多个客户端之间切换；部分流行客户端或闭源、或带商业捆绑、或来源不明，信任成本高。全球范围内同时存在少量由学术机构与志愿者运营的合法公共中继资源（如 VPN Gate），但缺乏一个干净、开源、全协议的统一入口。

本项目的动机是：提供一个**开源、非盈利、无账号无日志、全主流协议兼容**的统一客户端，让用户用一个软件管理自己合法获得的全部节点配置，并能合规接入官方授权的公共节点来源。

### 1.2 产品一句话定义

开源、非盈利的跨平台代理客户端：统一导入、管理和使用各主流协议的节点配置，支持用户自填、订阅导入与授权公共源插件，内核可插拔并渐进自研。（本句于 2026-11-12 随命名一并定版。）

### 1.3 目标用户

- 拥有自建节点或合法订阅、希望统一管理多协议配置的用户；
- 需要使用学术与公共中继资源（如 VPN Gate）的研究人员与普通用户；
- 重视开源透明、拒绝闭源商业客户端的用户与社区贡献者。

### 1.4 成功标准（v1.0）

- 兼容矩阵第一梯队协议全部可用且通过互通测试（第 15 章）；
- Windows 与 Android 双平台正式发布，安装包签名可验证、构建可复现；
- VPN Gate 公共源插件上线并带完整风险提示；
- 仓库治理、许可证、商标与安全响应流程全部落地（第 10、9 章）。

## 2. 可行性结论（讨论结论的书面化）

### 2.1 客户端本身：可行

全协议客户端的技术路径已被 v2rayN、NekoBox、Clash Verge Rev、Hiddify 等开源项目验证：成熟内核 + GUI 外壳 + 订阅解析 + TUN/系统代理 + 路由规则。本项目不承担「路径是否存在」的风险，只承担工程实现与质量风险。

### 2.2 自研全兼容内核：作为起点不可行，作为路线可行

「全兼容」的展开规模：协议层（Shadowsocks、Trojan、VMess、VLESS、Hysteria2、TUIC、WireGuard、OpenVPN、SoftEther 等）× 传输与安全层（TCP、WebSocket、HTTP/2、gRPC、QUIC、TLS、Reality、uTLS 指纹）× 平台网络层（TUN、DNS、IPv6、UDP、路由）。该组合是安全攸关代码，加密与握手实现错误将直接使用户在误以为安全的状态下裸奔。成熟内核（sing-box、Xray、SoftEther）是多年多人、在真实网络环境中持续对抗打磨的结果。

结论（已写入总表第 4 条）：第一版挂接成熟内核，自研从统一模型与外壳开始，内核模块按协议逐个自研替换，每个模块须通过与上游实现的差分互通测试后才许上线（第 6 章）。按此路线，自研目标不落空，且项目不必用 1–2 年（估算，见 14.3）换一个尚未面世的全自研内核。

### 2.3 公共节点：只有一个合法样板，且有明确边界

- **VPN Gate（日本国立筑波大学研究生院学术实验项目）**是目前全球唯一成规模、且明确邀请第三方接入的大学背景公共中继：官方提供公共 VPN 中继服务器列表，任何人可连接、无需注册，支持 SSL-VPN（SoftEther）、L2TP/IPsec、OpenVPN、MS-SSTP，并提供 CSV 列表供开发者制作自己的客户端应用。来源：https://www.vpngate.net/cn/about_overview.aspx
- 边界一：筑波大学仅托管其网站与列表，列表中的服务器由全球志愿者以自己的计算机提供，大学不对这些服务器负责。
- 边界二：VPN Gate 按其官方反滥用政策保留连接日志**三个月以上**（含源 IP、目标服务器、连接/断开时间等），各中继节点另保留数据包日志**至少两周**，日志可依法向警方、检察官、律师或法院披露。来源：https://download.vpngate.jp/en/about_abuse.aspx 因此 VPN Gate 只适合「可达性」用途，不适合高敏感隐私用途，本项目接入时必须逐字向用户提示（第 7.3 节）。
- 边界三：因其名单完全公开，其 IP 同时也是最容易被收集与封锁的一批；其主站在部分地区不可直接访问、依赖镜像。VPN Gate 只能作为公共源之一，不能作为唯一来源。
- 免费节点聚合站上标注为「大学/研究所」的 IP，多数只是 IP 段的 ASN 归属为学校（含学生宿舍志愿节点、配置错误的开放代理、被泄露的校内代理等），并非机构提供，禁止作为本项目来源（总表第 6 条）。
- Tor（含 Snowflake）、I2P 等研究背景项目出于抗封锁原理**故意不公开**节点 IP，只能以其自有客户端形态接入，无法拆解为 IP 名单供本项目使用，不列入来源规划。

### 2.4 总体可行性评级

| 组成部分 | 评级 | 说明 |
|---|---|---|
| 全协议客户端（挂接成熟内核） | 高 | 路径已被多个开源项目验证 |
| 外壳与统一模型自研 | 高 | 本项目核心资产，工作量可控 |
| 内核渐进自研 | 中 | 以年为单位的长期工程，须靠测试矩阵守门 |
| VPN Gate 公共源插件 | 高 | 官方授权明确，CSV 接口现成 |
| 自建公共节点池 | 不做 | 成本、滥用与法律风险与非盈利定位冲突 |
| 志愿者中继网络 | 远期评估 | 一期明确不做（总表负面清单） |

## 3. 产品定位与设计原则

1. **工具定位**：通用网络代理客户端。不预置立场、不预置节点、不预置分流规则之外的任何内容分发。
2. **本地优先**：全部配置与数据只存用户设备本地；无云同步、无账号、无服务器依赖。软件在完全无官方基础设施的情况下可永久运行——这是非盈利项目可持续的根基。
3. **诚实原则**：兼容范围、节点来源、日志风险、测速方法全部公开写明；不做「无日志」「绝对安全」「全网最快」等无法自证的营销表述。客户端自身的无遥测承诺以开源代码与可复现构建自证，不以口号自证。
4. **小白可用，专家可控**：默认路径三步内完成「导入—测活—连接」；高级参数（DNS、路由、传输层细节）完整开放给专家模式。
5. **上游尊重**：对所集成的开源内核与来源项目保留署名、遵守其许可证与使用条款；对 VPN Gate 等来源的接入方式以其官方条款为准，条款变更即复核接入资格。
6. **多语言原生（2026-11-12 用户锁定）**：本项目自始即为多语言项目，不是先做单语言再事后补翻译。界面文案自第一行代码起全部外置，禁止硬编码；语言以独立语言包维护、可单独增删与热更新；缺失翻译回退英文；语言切换免重启。具体规格见 8.1。

## 4. 全兼容协议矩阵

### 4.1 协议梯队

**第一梯队（v1.0 必须全部可用）**

| 协议 | 主要传输/安全层 | 一期实现来源 | 备注 |
|---|---|---|---|
| Shadowsocks（AEAD 全系） | TCP/UDP 原生 | 挂接内核 → 自研替换排序第 1 | 含 SS2022 |
| Trojan | TLS / WebSocket+TLS | 挂接内核 → 自研替换排序第 2 | |
| VMess | TCP / WS / HTTP/2，AEAD | 挂接内核 → 自研替换排序第 3 | 存量订阅占比高，不可缺 |
| VLESS | TCP / WS / gRPC + TLS / Reality / XTLS Vision | 挂接内核 → 自研替换排序第 4 | Reality 为全矩阵最难单项 |
| Hysteria2 | QUIC（UDP） | 挂接内核 → 自研替换排序第 5 | 与 TUIC 同属 QUIC 家族 |
| TUIC | QUIC（UDP） | 挂接内核 → 自研替换排序第 5（同批） | |
| WireGuard | 原生 UDP | 系统/成熟库实现，不自研密码学部分 | 只做配置管理与隧道编排 |
| OpenVPN | 原生 TCP/UDP | 成熟实现挂接 | 同时服务 VPN Gate 来源 |
| SOCKS5 / HTTP(S) 代理 | 原生 | 自研（简单协议，可首发自研） | 含账号密码认证 |

**第二梯队（v1.x 补齐）**

| 协议 | 形态 | 说明 |
|---|---|---|
| SoftEther（SSL-VPN） | 独立内核插件 | VPN Gate 的主力协议，经 SoftEther 客户端组件接入 |
| L2TP/IPsec | 系统 VPN 能力编排 | 不进代理内核，走操作系统原生 VPN 栈 |
| MS-SSTP | 系统/SoftEther 编排 | 同上 |
| AnyTLS 等新兴协议 | 挂接内核跟进 | 以 sing-box 上游支持为准，进矩阵须过互通测试 |

**明确不支持**

- 无公开规范的私有协议、厂商闭源协议；
- 依赖破解、盗版授权或未授权账号的任何接入方式。

### 4.2 订阅与链接格式（v1.0 全部支持）

- 分享链接：`vless://`、`vmess://`、`trojan://`、`ss://`、`hysteria2://`（含 `hy2://`）、`tuic://`、`wg://` / WireGuard 配置文件、OpenVPN `.ovpn` 文件；
- 订阅格式：sing-box JSON、Clash YAML、V2Ray 订阅（base64）、原始链接列表（base64 与明文）；
- 公共源格式：VPN Gate CSV（经来源插件，见 7.3）；
- 导入方式：粘贴、扫码、文件导入、订阅 URL 定时更新、剪贴板识别。

### 4.3 矩阵维护规则

矩阵为项目对外承诺的唯一口径，置于仓库与官网首页；任何协议从「规划中」升为「已支持」，必须以第 15 章互通测试通过记录为据，禁止先宣传后实现。

## 5. 总体架构

### 5.1 分层结构

```
┌─────────────────────────────────────────────┐
│ UI 层（按平台实现：桌面 / Android）            │
│  节点列表 · 分组 · 测活 · 连接 · 设置 · 日志视图 │
├─────────────────────────────────────────────┤
│ 应用服务层（自研，Go）                        │
│  配置管理 · 测活调度 · 路由策略 · 更新检查      │
├─────────────────────────────────────────────┤
│ 统一节点模型层（自研，项目核心资产）            │
│  Node / Group / Source 统一数据模型与校验      │
├──────────────┬──────────────┬───────────────┤
│ 解析器（自研） │ 来源插件（自研）│ 内核适配层（自研）│
│ 订阅/链接解析  │ VPN Gate 等   │ KernelAdapter  │
├──────────────┴──────────────┴───────────────┤
│ 内核层（可插拔）                              │
│  sing-box（主）· SoftEther/OpenVPN（VPN 类）   │
│  · 自研内核模块（按第 6 章逐步替换）            │
├─────────────────────────────────────────────┤
│ 平台网络层                                   │
│  TUN / 系统代理 / VpnService · DNS · 路由     │
└─────────────────────────────────────────────┘
```

设计要点：UI 与内核之间隔着统一模型与适配层两层抽象，任何一端更换（换 UI 框架、换内核、自研模块替换）不影响另一端。这是「渐进自研」在架构上的落点。

Step 2 审计回写（2026-11-12，见 docs/step2-许可证审计.md）：OpenVPN 2.x 为 GPL-2.0-only，不得与本项目 GPLv3 代码同二进制链接，其在内核层的集成形态固定为**独立进程适配**（进程内需求改走 OpenVPN 3 库路线）；Windows TUN 所需 wintun.dll 只使用官方预编译签名版（专有 Prebuilt Binaries License），不自建、不修改。

### 5.2 统一节点模型（核心字段示意）

```json
{
  "id": "uuid",
  "name": "示例节点",
  "protocol": "vless",
  "server": "example.com",
  "port": 443,
  "credential": {"uuid": "…", "flow": "xtls-rprx-vision"},
  "transport": {"type": "tcp", "path": null, "host": null},
  "security": {"type": "reality", "serverName": "…", "publicKey": "…", "fingerprint": "chrome"},
  "udp": true,
  "source": {"kind": "subscription | manual | plugin", "ref": "来源标识", "authorization": "授权依据标识"},
  "group": "分组名",
  "lastTest": {"at": "ISO-8601", "latencyMs": 0, "ok": true}
}
```

模型以 JSON Schema 定版并纳入仓库 `spec/` 目录；所有解析器与来源插件只许输出该模型，所有内核适配器只许消费该模型。模型版本化，变更走 RFC 流程（第 10 章治理）。

### 5.3 内核适配层接口（最小集）

- `ValidateConfig(model) → errors`：下发前静态校验；
- `Start(model, platformOptions)` / `Stop()` / `Status()`：生命周期；
- `TestHandshake(node) → latency, error`：真实协议握手测活（禁止以 ICMP ping 冒充节点可用性）；
- `QueryTraffic() → up, down`：流量统计；
- `Capabilities() → protocolMatrix`：内核自报支持矩阵，UI 据此灰化不支持项，禁止静默失败。

### 5.4 平台网络层要点

- Windows：TUN 模式基于 Wintun；系统代理模式为无驱动备选路径；
- Android：基于 VpnService 实现 TUN，不要求 Root；
- DNS：内置防泄露策略（远程解析优先、禁止明文回落到本地运营商 DNS 的默认策略须经用户确认）、支持 DoH/DoT 配置项；
- 全局「断网保护」（kill switch）：隧道异常断开时阻断直连流量，桌面与 Android 均为 v1.0 必备项并列入验收（第 15 章）。

### 5.5 本地存储与更新

- 配置文件本地加密存储（密钥由用户口令派生，用户可选择不设口令并承担相应风险，界面明示）；
- 导出配置须二次确认并提示「配置含凭据，等同密码」；
- 软件更新：仅检查官方发布通道，更新包必须验签通过才可安装（第 9.4 节）；无强制更新、无静默更新。

## 6. 自研内核渐进路线

### 6.1 替换排序与理由

排序按「实现难度低 → 高、存量用户多 → 少」综合排定，与 4.1 表一致：

| 批次 | 协议 | 理由 |
|---|---|---|
| K-1 | SOCKS5 / HTTP、Shadowsocks | 规范小而稳定，先跑通自研模块的全套流程（实现—测试—替换—回滚） |
| K-2 | Trojan、VMess | 结构清晰，存量大，替换收益高 |
| K-3 | VLESS（含 TLS） | 主体不难，难在 Reality 与 Vision，单独立项攻坚 |
| K-4 | Reality / XTLS Vision | 全矩阵最难：TLS 指纹与抗探测行为必须与主流实现逐字节对齐行为特征 |
| K-5 | Hysteria2、TUIC | QUIC 家族，依赖 QUIC 栈成熟度，最后替换 |

WireGuard 的密码学与隧道实现永不自研（只用成熟实现），理由：自研密码学实现是安全红线，不在任何批次内。

### 6.2 替换门禁（每批次通用）

一个自研模块替换挂接实现，必须同时满足：

1. 与至少两个主流服务端实现完成互通测试并留存记录；
2. 与挂接内核做差分测试：同一批节点样本集（含异常与边界样本）下，两者握手成功率、出站行为一致性达到门禁阈值（阈值在 Step 24 定版）；
3. 通过模糊测试（fuzzing）规定时长无崩溃与无内存安全问题；
4. 保留一键回退到挂接内核的开关至少两个正式版本。

### 6.3 长期形态

全部批次完成后，项目拥有完整自研内核，挂接内核降为可选兼容后端。此形态为长期目标，不设对外承诺日期；进度以批次为单位在路线图公开，禁止以「全自研」做先行宣传（与 4.3 同一诚实原则）。

## 7. 节点来源治理

### 7.1 来源分级（唯一口径）

| 级别 | 定义 | 处置 |
|---|---|---|
| A 级 | 来源方官方明确授权第三方接入并提供公开接口（如 VPN Gate CSV） | 可做官方插件，须登记授权依据与条款链接 |
| B 级 | 用户自行提供（自填、订阅链接、文件导入） | 客户端只做解析与校验，来源合法性由用户负责，界面一次性明示 |
| C 级 | 社区维护者以本人名义发布的公开订阅，授权状态不明 | 不预置、不推荐；用户自行添加的，按 B 级处理 |
| D 级 | 泄露、共享、扫描、盗号所得节点 | 禁止：不得进入官方插件、仓库、文档与推荐位；发现官方渠道内出现即下架处理 |

### 7.2 来源插件规范

- 每个插件独立仓库目录，含 `manifest`（来源名、运营方、授权依据、条款 URL、数据格式、更新频率）；
- 插件输出必须为统一节点模型并打上 `source.authorization` 标识，UI 在节点详情中展示来源与授权依据，用户可溯源；
- 插件只能拉取、解析、测活，不得执行任意代码，不得上报用户数据；
- 来源方条款变更或撤销授权的，插件须在一个版本内下线。

### 7.3 VPN Gate 插件规格（一期唯一官方插件）

- 数据接入：拉取官方 CSV 服务器列表（含镜像地址轮换策略），字段映射为统一模型，协议限其支持的 SoftEther / OpenVPN / L2TP / SSTP；
- 测活：以真实握手为准入，列表按国家/地区分组，标注志愿者属性；
- **强制风险提示**（首次启用时整页展示、节点详情常驻一行）：「VPN Gate 为筑波大学学术实验项目，节点由全球志愿者提供；其官方政策保留连接日志三个月以上并可依法披露，节点运营者可接触经其转发的未加密流量。本来源适合一般可达性用途，不适合高敏感用途。」用户未确认不得启用；
- 合规：接入方式以 VPN Gate 官方条款为准，禁止将本插件用于批量扫描、滥用或转售。

### 7.4 用户自有来源

用户自填与订阅导入为一等功能（一期即交付），含订阅定时刷新、流量与到期信息解析（订阅方提供时）、重复节点去重与分组管理。

## 9. 安全与隐私

### 9.1 威胁模型（摘要）

- 保护对象：用户的节点凭据（等同密码）、真实 IP、流量内容、配置清单；
- 假想对手：恶意节点运营者、冒牌客户端分发者、被入侵的下载通道、本地恶意软件、对用户设备有物理访问权者（仅部分缓解）；
- 明确不在保护范围：用户所选节点自身的日志与审查行为（客户端不可控，只能靠 7.3 式告知）、用户所在地法律风险（用户自担）。

### 9.2 客户端安全要求

- 零遥测：不集成任何统计、崩溃上报、广告 SDK；崩溃日志只存本地，用户手动导出才离开设备；
- 凭据保护：本地加密存储（5.5），内存中尽量缩短明文驻留；
- 更新与分发验签：全部安装包与更新包签名，校验失败拒绝安装并提示；
- 可复现构建：发布构建流程公开，第三方可按文档从源码构建出比特一致或可验证等价的产物，并公布校验方法；唯一例外为 wintun.dll（官方预编译专有许可组件，Step 2 审计 F-2），须记录其官方版本号与校验值并随包标注，Windows 安装包不得对外宣称「100% 开源」；
- 依赖治理：依赖锁定与定期审计，安全公告走 GitHub Security Advisory 流程。

### 9.3 节点风险告知（产品内义务）

除 VPN Gate 专项提示外，任意第三方节点详情页常驻提示：「节点运营者可以看到你的出口 IP 行为并可能记录日志；请只使用你信任来源的节点。」该提示不可关闭，只能确认收起至详情页一行。

### 9.4 漏洞响应

- 仓库设 `SECURITY.md`：私密报告通道、响应时限承诺（确认 72 小时内、修复按严重级排期，为目标值非法律承诺）；
- 严重漏洞修复后发布安全公告并建议用户升级，公告不披露未修复细节。

## 10. 开源治理与许可证

### 10.1 许可证裁定

- 主仓库许可证：**GPLv3**（总表第 8 条）。裁定理由：本项目最大的现实威胁不是「没人用」，而是第三方将免费客户端闭源打包、植入广告或恶意代码后转售，既毁项目声誉又害用户。GPLv3 的 copyleft 条款使此类打包必须继续开源，是成本最低的防御。
- 兼容性事实基础：本项目一期主挂接内核 sing-box 为 GPL-3.0-or-later（以其仓库 LICENSE 原文为准，Step 2 审计复核），整体采用 GPLv3 与之兼容；SoftEther 为 Apache License 2.0，可在 GPLv3 项目中合规集成（保留其许可证与署名）。

- 文档与规范（`spec/` 下的统一模型等）采用宽松条款单独授权，以便其他项目兼容实现，促进生态互通；代码与文档分开授权在仓库中明示。
- Step 2 审计建议（F-5）：主仓库落地时明确采用 GPL-3.0-or-later（与 sing-box 的 or-later 授权及 Xray-core 的 Secondary License 路径衔接最顺），属措辞澄清、不改变 GPLv3 路线，待 Step 4 建仓时定版。

### 10.2 商标与品牌

- 代码开源不等于品牌开源：项目名称、Logo 的使用规则以单独的商标政策文件发布，未经许可不得以项目名义分发修改版（修改版须改名），此为防冒牌的必要措施，与 GPLv3 不冲突；

## 14. 分步实施计划

## 附录 A：VPN Gate 事实卡（接入依据）

- 运营方：日本国立筑波大学研究生院学术实验项目（与 SoftEther 项目同源）；
- 形态：官方维护公共 VPN 中继服务器列表，服务器由全球志愿者提供，大学仅托管网站与列表；
- 协议：SSL-VPN（SoftEther）、L2TP/IPsec、OpenVPN、MS-SSTP；
- 接入：无需注册；官方提供 CSV 列表供开发者制作客户端（本项目据此定为 A 级来源）；
- 日志：官方反滥用政策载明连接日志保留三个月以上（源 IP、目标服务器、连接/断开时刻、协议类型等），中继节点数据包日志至少两周，日志可依法向执法与司法机关披露；
- 定位结论：合法、可用、须强提示；只解决可达性，不提供匿名性。
- 来源链接：https://www.vpngate.net/cn/about_overview.aspx ；https://download.vpngate.jp/en/about_abuse.aspx

## 附录 D：术语

- **节点**：一个可连接的代理/VPN 服务器配置，含地址、协议与凭据；
- **来源**：节点的获得渠道，分用户自有与插件公共源两类（第 7 章）；
- **挂接内核**：一期经适配层集成的成熟开源内核；**自研内核**：本项目按第 6 章自研替换的内核模块；
- **测活**：以真实协议握手验证节点可用性并测延迟的行为，区别于网络层 ping；
- **断网保护（kill switch）**：隧道异常时阻断一切直连流量的机制。
