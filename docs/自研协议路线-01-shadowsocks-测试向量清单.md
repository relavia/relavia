# 自研协议路线 · 01 附件 — Shadowsocks 测试向量清单（设计）

> 配套 `docs/自研协议路线-01-shadowsocks.md` §5。本文是**清单设计**：向量数据文件（JSON 元数据 + 二进制流文件）在实现阶段按本清单生成，存入测试台 `testdata/shadowsocks/`，每条向量一个条目，字段固定为：
> `id / 优先级 / 类别 / 方法 / 输入（口令或 PSK、盐、nonce 初值、明文、方向） / 期望（中间值与/或密文与/或失败分类） / 来源（双源交叉的两个出处） / 备注`。
> 密钥类输入一律为本清单专用的测试值（标注 `TEST-ONLY`），禁止与任何真实节点凭据相同。
> 优先级：P0 = 门禁 G3 的 100% 通过集；P1 = ≥98% 且未过须逐条裁决。

| ID | 优先级 | 内容 | 期望 |

| NEG-01 | P0 | 响应流 tag 篡改 1 比特 | 首个受影响块开封失败，`handshake_failed`，不吐明文 |
| NEG-02 | P0 | 流在盐中途、长度块中途、tag 中途三处截断 | 干净 EOF/失败，不挂死、不 panic |

## F. 生成与维护规则

1. 每条 P0 向量的期望值须双源交叉（规范附例 / shadowsocks-rust 实测 / sing-box 实测取其二），来源写入条目；双源不一致时该向量冻结并走主规格 §4.6 G4 裁决，不许挑一个顺手的填上。
2. 向量文件只增不改：已发布向量的期望值变更必须新开条目并注明取代关系，防止「改期望迁就实现」。
3. 生成工具（脚本）随向量一同入库，任何人可从清单输入重新生成并比对，生成结果不一致即测试台缺陷。
4. 本清单与主规格 §6 待核清单联动：§6 第 1–4 项核对结论直接决定 D 类向量的头部期望值，核对未完成前 D 类只登记条目、不填期望。

## G. 更正记录

- **2026-11-23（差分跑批发现）**：C 类 W17-01…04、W17-06 的 `expected.responseStream` 误按请求方向模型（地址头 + 载荷）生成；实测（shadowsocks-rust v1.25.0 + sing-box v1.14.4 入站）证明 2017 TCP 响应流只有载荷、无地址头（详见主规格 §6 第 8 条）。按 F.2 纪律处置：原期望字节保留在向量文件中并加 `withdrawn` 标记（仅标记 `responseStream` 字段，`requestStream` 继续有效），正确响应流以新条目 **W17-21…24、W17-26**（与 W17-01…04、W17-06 同参数）入库。NEG-01 的基流同源，其篡改点落在长度块内、与响应模型无关，保留并已在生成器注释中注明。教训：生成器与被测引擎同源时，向量层双源交叉会同误——线上流向量的第二来源必须是独立参考实现的实测，差分台（主规格 §4）不可省。
