# 真机连接失败诊断（2026-11-14）

对象：第四轮测试包真机实测（用户 2026-11-14 11:15–11:19，安卓）——VPN Gate
池刷新成功（99 节点 / 9 组 / 22 tcp-reachable），但点连接后 OpenVPN 3 core 对
219.100.37.209:443、219.100.37.127:443 反复 "Server poll timeout"，任何节点
都连不上；用户同时报告「检测不动、关掉还会自己重新连接、每个 IP 要点三点
菜单才出连接按钮」。

本文件只诊断与出证据，不改代码。方法：重拉官方列表核对服务器存活；用桌面
进程适配（core/openvpn + OpenVPN 2.6.9 rig 形态）从本沙盒对同一服务器做
真实握手对照；官方配置 / 桌面渲染 / 安卓渲染三方逐行比对；连接路径代码审读。

先说环境限制（影响证据效力，先行声明）：**本沙盒的原始 TCP 出口被策略代理
拦截**——任意对外 TCP 连接都被本地代理终结并回一段英文横幅
（原文 "muse: Other TCP connections is turned off for this assistant."）。
OpenVPN 视角的原文证据：官方配置直跑时收到
"Bad encapsulated packet length from peer (28021)"（28021 = 0x6D75，即横幅
首两字节 "mu" 被当成 OpenVPN 包长）随即 "Connection reset, restarting"。
因此沙盒内一切「对公网服务器的握手」都在代理处终止、从未到达服务器；
沙盒实验能证明的与不能证明的在下文分开标注。曾尝试用第三方在线端口检测
（check-host.net）取第二个观察点，页面抓取超时未获结果，未重复尝试。

## 2. 沙盒桌面真实握手实验

OpenVPN 二进制：按 docs/openvpn进程适配.md §3 同法从 Ubuntu 官方归档直拉
`openvpn_2.6.9-1ubuntu4_amd64.deb`（SHA256 `73bb9039c930d2…` 与文档登记值
一致），版本 2.6.9 / OpenSSL 3.0.13。

实验 A（对照，官方配置原文）：官方 .ovpn 原样 + rig 形态覆盖
（`--dev null --ifconfig-noexec --route-noexec`），50 秒限时。结果：TCP
瞬间「连通」（实为连到沙盒代理），首包即代理横幅 → bad packet length →
Connection reset 循环至超时。**未到达服务器**，对服务器无证明力。

实验 B（处理组，我们的完整管线）：临时诊断测试（已删除、未入库）走生产
代码路径——`parsers.ParseVPNGateCSV` 解析上述 CSV → specnode 转换 →
`buildConfig` → 桌面适配器 `TestHandshakeNode`（DevOverride=null +
ifconfig-noexec/route-noexec，与 rig 同形态）。结果：进程正常拉起、配置
正常生成，在同一代理横幅处进入 reset 循环，最终被分类为
`connect_timeout`，恰在配置的 60 s 上限收束（管理状态 RECONNECTING /
connection-reset）。同实验 A 倒在同一步、同一种字节上——渲染管线没有
引入任何额外失败点。

实验 C（正对照，我们的管线对已知健康服务器）：既有 rig 测试
`TestRigHandshakeAndLifecycle` 当日复跑 **PASS**（回环真实 OpenVPN 服务端，
握手成功、延迟 3.99 s、全生命周期 11.7 s）。我们的客户端栈对可达的
服务器工作正常。

小结：沙盒区分不了「服务器死」与「用户网络不通」（两个实验都死在沙盒
自己的代理上，与服务器无关）；能区分的是——配置与管线无自身失败
（实验 B/C），45 秒级超时与失败分类在桌面侧真实生效（实验 B）。

## 3. 三方配置比对（官方 vs 桌面渲染 vs 安卓渲染）

219.100.37.209 官方配置指令集（证书块略）：
`dev tun`、`proto tcp`、`remote 219.100.37.209 443`、`cipher AES-128-CBC`、
`data-ciphers AES-128-CBC`、`auth SHA1`、`resolv-retry infinite`、`nobind`、
`persist-key`、`persist-tun`、`client`、`verb 3`，内联 `<ca>/<cert>/<key>`。
**无 auth-user-pass，无 tls-auth / tls-crypt / static key。**

机器比对结果：

| 对比 | 结果 |
|---|---|
| 官方 vs 安卓 RenderProfile 输出 | **指令多重集完全一致，零差异**；实测运行 rewritten 为空集（无一条被剥离/改写） |
| 安卓 RenderProfile vs 桌面 buildConfig | 仅差桌面生产附加的**管理块**（management 端点、management-query-passwords、用认证时 auth-nocache）——进程控制工件，非会话语义（core/openvpn/render.go:23-31、genconfig.go:112-148）；诊断中的 dev null / ifconfig-noexec 是 rig 期权，不入生产 |

同源性：两端共用同一 builder——`RenderProfile`（render.go:62）内部即
`buildPassthrough`（render.go:70）；桌面 `buildConfig`（genconfig.go:112）
走同一 `buildPassthrough`（genconfig.go:150）后追加管理块。VPN Gate 节点
恒为全文模式（core/parsers/files.go ParseVPNGateCSV → ParseOpenVPNConf →
credOpenVPNContent）。

逐项答复：

- **auth 方式**：VPN Gate 的 OpenVPN 配置以**内联共享客户端证书**认证，
  不是 vpn/vpn 口令（vpn/vpn 是其 SoftEther/L2TP 侧的惯例）。我们的解析
  不给这类节点设用户名（实测节点 Username=""），于是 genconfig 的
  「有用户名才补 auth-user-pass」（genconfig.go 约 204-209 行）不触发，
  RenderProfile 实测 UsesAuth=false，安卓 Ovpn3Client.runSession 仅在
  用户名非空时 ProvideCreds——两端行为一致。且失败发生在服务器对最初
  控制包零应答阶段，早于任何认证，auth 不是本次失败点。
- **tls-auth/static key**：官方配置没有，我们也没有凭空生成——一致。
- **cipher / data-ciphers / auth SHA1**：两端原文透传。手机日志里 core
  把 data-ciphers 列入 "Unsupported option (ignored)" 是 OpenVPN 3 core
  自身的注记（它同时列了 resolv-retry、persist-key、persist-tun）；连接
  卡在密码协商之前的零应答阶段，与此无关。
- **remote 协议与端口**：tcp / 443，原文透传，实测节点 Server/Port 正确。
- **resolv-retry / persist 来源**：**服务器下发**（官方配置原文自带），
  不是我们写入的。见 §4⑤。

## 4. 安卓连接路径代码答复

### ① 45 秒上限在安卓是否真实生效

生效——在 Go 引擎层。`ovpn3Engine.start`（app/libboxbind/ovpn3engine.go:179-183）
以 `openvpn.DefaultConnectTimeout`（core/openvpn/openvpn.go:43，45 s）为界
等待 CONNECTED；到期即 `bridge.StopOvpn3Session()` 并以 connect_timeout
失败返回（ovpn3engine.go 约 196-205 行）。手机日志与此严丝合缝：.209 会话
11:16:45 起、11:17:29 终，约 44 s（4 个 10 s poll 周期），随后是**新会话**
开始的横幅。用户感知的「超过 90 秒」是多个会话**串联**的总时长，不是
单个会话超限。（例外注记：等系统 VPN 授权弹窗走另一条 3 分钟预算
ovpn3engine.go:148，本次授权已预先给出，不在路径上。）

### ② 失败后是否自动级联下一个候选

`Service.Connect`（app/service/service.go:426）与
`Service.AutoSelectAndConnect`（service.go:452）**都不级联**：单节点、
单尝试、失败即返回。串联来自一键连接链的**检查阶段**：
`runHeroChain`（app/ui/ui.go:583）→ `heroChainSteps`（ui.go:617）依次
刷新 → `TestGroup(ctx, AllGroups)`（ui.go:631）→ `AutoSelectAndConnect`
（ui.go:635）。`TestGroup`（service.go:385）按显示顺序**逐个**探测；
安卓上 OpenVPN 节点的探测就是一次**完整的 ovpn3 会话**
（TestHandshakeNode → ovpn3engine.go 的 start，含同样的 45 s 上限）。
99 个节点逐个探测、每个不通的都吃满 45 s，链的总预算只有 5 分钟
（ui.go:599）——检查阶段必然中途耗尽，绝大多数节点停在「还没检查」
（与用户截图状态逐字吻合：.209 检查失败、其余还没检查），随后
AutoSelectAndConnect 只剩零星已测通节点可选，通常直接无可用节点。
日志里 .209 → .127 的先后顺序即列表显示顺序的逐个探测，与此为唯一
吻合的代码路径（强推断，日志无阶段标记可再细分）。另注：刷新日志的
「22 tcp-reachable」是插件的 TCP 拨号预检（plugins/vpngate/probe.go），
只证明 SYN 有应答，不证明 OpenVPN 控制通道有应答——两者被当成同一
回事是误导来源之一。

### ③ App 启动是否自动恢复/重连上次会话

应用层没有自动重连。`LastConnectedNodeID` 被持久化
（app/service/store.go:84，Connect 成功时写入 service.go:442），但只被
读来渲染首屏卡片（heroReconnect「连接上次」按钮 views.go:385、为你选好
列表 views.go:600），没有任何启动路径调用 Connect；全部 Connect 调用点
都是用户手势（ui.go:556、ui.go:635 的一键链）。ui_android.go:83 的 1 秒
定时器只做窗口重绘。Kotlin 侧 ACTION_OVPN3_START 虽返回 START_STICKY
（RelaviaVpnService.kt:84），但系统重启服务时 pending 配置只存内存且
首跑即消费，重启后取到 null 即自行收摊（RelaviaVpnService.kt:140-146），
不会复活会话。

**用户感知的「关掉还会自己强行打开」真源在链不在重连**：一键链运行在
独立的 5 分钟背景 ctx 上（ui.go:599），Disconnect 只调 engine.Stop 停掉
**当前**那个探测会话（ovpn3engine.go:224-247），从不取消链的 ctx；
TestGroup 随即把**下一个**节点的会话拉起来——VPN 服务、前台通知、core
进程随之一次次复活，直到链走完或 5 分钟耗尽。runAsync 的普通操作
（ui.go:501，90 秒 ctx）同样无取消句柄。

### ④ Disconnect 是否确实终止 core 会话轮询

对**正在进行的那一个会话**：是。链路为 UI → Service.Disconnect →
ovpn3Engine.Stop（ovpn3engine.go:224）→ bridge.StopOvpn3Session →
Ovpn3BridgeImpl.stopOvpn3Session（Ovpn3BridgeImpl.kt:74-96）：
`Ovpn3SessionController.requestStop()` 直达活 core 对象的 `stop()`，
另发 ACTION_OVPN3_STOP 让尚在拉起中的服务收摊
（RelaviaVpnService.kt:96-105）；Go 侧同时唤醒挂起的 start 等待者以
取消错误收束。core 的 connect() 轮询被 stop 打断。
局限不在停止路径本身，而在调用方：没有任何机制阻止链/探测循环停完
一个又开下一个（见 ③），用户看到的净效果就是「断不开」。
### ⑤ resolv-retry infinite 的剥离/覆写机制

没有。全文模式的剥离表 `stripDirectives`（core/openvpn/genconfig.go:48）
只含管理块、守护/日志重定向、提权、脚本钩子、Windows 服务控制几类；
resolv-retry、persist-key、persist-tun、connect-retry、server-poll-timeout
既不剥离也不覆写，RenderProfile 亦不追加任何重试类指令（§3 的零差异
即此）。影响分两端：桌面 OpenVPN 2.x 会真的执行 resolv-retry infinite，
靠适配器 ConnectTimeout + 进程回收兜底；安卓 ovpn3 core 根本不认这些
OpenVPN 2 选项（手机日志的 ignored 注记），其约 10 秒一轮的 poll 重试
是 core 内部行为，唯一的缰绳是 Go 引擎的 45 秒上限。

## 5. 根因排序

1. **[强证据 · 我方设计] 一键链的检查阶段在结构上注定失败。**
   全量 99 节点逐个全会话探测 × 每节点最长 45 s × 链总预算 5 分钟，
   且探测顺序为显示顺序（不按 CSV 自带的 Ping/Score 排序）、无「测通
   几个即停」。健康网络下尚可，用户网络下必死。代码定位见 §4②。
   这同时解释了「不能检测」。
2. **[强证据 · 我方设计] 链不可取消，Disconnect 停错了层。**
   断开只停当前会话、不取消链，探测循环逐个复活 VPN 服务——即用户
   报告的「关掉了自己也会强行打开自动连接」。代码定位见 §4③④。
3. **[强证据排除法 · 网络路径] 单节点连不上是用户网络到站路径不通。**
   .209 在册且挂着 179 个他人会话（§1），配置与官方零差异且管线经
   rig 验证（§2 实验 C、§3）；手机侧两台不同服务器呈同一签名——TCP
   建起、OpenVPN 控制通道在每个 10 s poll 内零应答。这只剩路径层
   （运营商/中间环节对 OpenVPN-over-TCP 的过滤或限速、或服务器对
   来源网络的过滤）未被满足；证据无法定位到具体哪一跳，沙盒自身在
   拦截代理之后、无第二个干净观察点，如实标注到此为止。
4. **[已排除] 服务器死亡/列表陈旧（对 .209）**：§1 证伪。.127 已下线
   属正常轮换，但它在用户列表里排第二、白吃一整段 45 s 预算——属
   排序问题、并入第 1 条。
5. **[已排除] 配置渲染错误**：§3 三方零差异、实测 rewritten 为空集。
   vpn/vpn 口令说亦不适用（证书认证，见 §3）。
6. **[次要] 误导性信号**：刷新期「22 tcp-reachable」把 SYN 应答说得
   像可用性（§4②）；日志页被 core 原文刷屏（用户截图二）淹没了阶段
   信息。均非根因，属修复清单的文案/呈现项。

附带确认（非问题）：引擎层 45 秒上限真实存在（§4①）；给定可达服务
器时桌面栈握手正常（§2 实验 C）；安卓 profile 与官方逐指令一致（§3）。

## 6. 建议修复清单（仅建议，未实现）

1. **一键链改「连即测」**：按候选顺序逐个**连接**（短单试上限，如
   12–15 s），首个 CONNECTED 即停；全量 TestGroup 只保留给显式的
   「检查全部」入口。候选排序用 CSV 的 Ping/Score 与既有 LastTest，
   不用显示顺序。
2. **检查阶段设双预算**：单节点探测上限与总上限都远小于现状
   （如单节点 8–10 s、总 60 s），测通 3 个即收；探测失败原因为
   connect_timeout 的节点在同一链内不得被 AutoSelect 立即重试。
3. **Disconnect 取消链**：runHeroChain / runAsync 保存 cancel 句柄，
   断开与新操作都先取消在跑的链；engine.Stop 之外，链 ctx 必须同停。
4. **预检结果分级呈现**：tcp-reachable 只标「网络可达」类弱信号，
   不与握手测通混排；节点行状态文案区分「未检查 / 可达未握手 /
   握手失败 / 可用」。
5. **重试参数收口（需另行验证）**：评估在 RenderProfile 侧为 ovpn3
   设置 ClientAPI_Config 的连接超时类参数、桌面侧对 passthrough
   追加 connect-retry 上限的可行性与副作用，再决定是否改「服务器
   配置原文透传」的现行口径——本诊断不预判。
6. **日志降噪**：UI 日志对 core 的重复 poll 行做折叠计数，阶段事件
   （刷新/检查/连接/失败原因）置顶呈现，方便用户与巡逻定位。
7. **真机复测口径**：修复后以同一台 .209 级别节点（在册、高会话数）
   在用户网络实测一键链全程计时；L5 公网握手验收仍以此为准，
   沙盒实验不得替代（§2 环境限制）。

## 7. 修复落地（2026-11-14 修复批）

§6 清单已由真机复测修复批实现（提交见本文件所在仓库当日
main 历史，批次题名 "Make the one-tap chain cancellable,
tier the probing, and fix the device-reported defects"）。
逐项对照：

1. **连即测 + 候选排序**（§6.1）：新增服务层 OneTapConnect
   ——候选按证据分级排序（已握手实测延迟〔含协议偏好的
   近似桶/类别序，与原 AutoSelect 同口径〕> 名单自带
   Ping/Score〔插件解析字段经 Store 持久化补齐〕> 其余显示
   序；弱加密全程降级不变），先对靠前候选做快速 TCP 预检
   （并发、单节点 ≤3s），再对最优 ≤5 个依次真实连接、单个
   ≤15s，首个成功即停且按真实握手记账；全失败按类别给人
   话（全部无响应/超时 → err.no_response）。
2. **双预算与不重试**（§6.2）：预检组总预算 45s；实连尝试
   ≤5 个 × ≤15s；预检刚失败的节点同一链内不重试（只试
   预检未覆盖的候选）；节点页「检查全部」与行内「检查延
   迟」改走同一快速预检（并发、逐个落地、总时长有界），
   文案统一「检查延迟」口径、不称「可用」；全会话探测只
   保留给单节点手动连接（45s 上限不变）。
3. **Disconnect 取消链**（§6.3）：服务层可取消操作注册表
   （BeginOp/CancelActiveOp）；Disconnect 语义改为「停一
   切」——先取消在跑的链再停引擎；UI 的断开绕过 busy 门
   直达（旧实现在链运行中会被 runAsync 丢弃）；英雄进度
   卡新增取消按钮；ovpn3 引擎的 CONNECTED 等待改受调用方
