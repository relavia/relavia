# 自研协议路线 · 01 — Shadowsocks 规格与差分测试计划

> 定位：方案书第 6 章「自研内核渐进路线」K-1 批次中 Shadowsocks 部分的**实施规格与测试计划**，对应第 14 章 Step 21（自研框架与测试台、6.2 门禁阈值定版）与 Step 22（K-1 批次替换）的 Shadowsocks 切片。
> 本文只定规格、接线与门禁，**不含实现代码**；实现另行立项，须按本文门禁逐项过关后才许替换默认路径。
> 基线事实（2026-11-23 核对）：`core/kernel.Adapter` 接口已定版（Step 6，7 个方法）；现行 Shadowsocks 出站由 `core/singbox` 适配器提供，锁定 sing-box **v1.14.4**（构建标签 `with_quic with_utls with_wireguard with_gvisor`），其能力矩阵中 Shadowsocks 为 raw 传输 + AEAD 安全层、UDP 可用，方法集见 `core/singbox/capabilities.go` 的 `ssAEADMethods`。

## 0. 红线（先于一切技术内容）

1. **严禁自造密码学。** 本模块只许把已审的标准原语按公开规范组装：AES-GCM、ChaCha20-Poly1305、XChaCha20-Poly1305、HKDF、BLAKE3 的实现一律取成熟库（见 §2.4）；不许自研分组密码/哈希/AEAD 构造，不许自创 KDF，不许「改良」规范里的任何密码学步骤。协议逻辑（分帧、头部、会话管理）可以自研，密码学原语不可以。
2. **WireGuard 不在此列**：其密码学与隧道实现永不自研（方案书 6.1），与本文无关。
3. **诚实口径**：门禁未全过之前，对外矩阵中 Shadowsocks 的实现来源仍写作「挂接内核」；禁止以「全自研」做先行宣传（方案书 6.3）。
4. 凭据（密码/PSK）按方案书 9.1 当密码对待：不进日志、不进测试报告明文；测试向量中的密钥一律为专门生成的测试值并明确标注不可用于生产。

## 1. 目标与非目标

### 1.1 目标

用自研实现替换 **sing-box 适配器中的 Shadowsocks 客户端出站**（outbound），使其经同一个 `kernel.Adapter` 接口对外服务，上层（服务层、UI、统一节点模型）零感知、零改动。自研模块通过本文差分 + 模糊门禁后，按节点/按配置可切换，默认路径切换与回滚按 §3.3 纪律执行。替换完成后，sing-box 仍保留：承担其余全部协议的出站，并长期充当 Shadowsocks 的**差分对照组**与回退后端（方案书 6.2 第 4 条：回退开关至少保留两个正式版本；本文建议长期保留，不预设删除日期）。

### 1.2 范围内（v1 替换面）

| 维度 | 纳入 |
|---|---|
| 角色 | 仅客户端出站（含 `TestHandshake` 的真实握手拨号路径） |
| 协议代际 | Shadowsocks AEAD（2017，SIP004）+ Shadowsocks 2022（SIP022），方法清单见 §2.2 |
| 承载 | TCP 流、UDP 数据报，双路均为必备（方案书 4.1 口径：TCP/UDP 原生） |
| 地址形态 | IPv4（ATYP 0x01）、域名（0x03）、IPv6（0x04）三类目标地址 |
| 模型字段 | 统一节点模型 `credential.method`、`credential.password`、`udp` 开关、server/port（§2.3 对应表） |
| 互通对象 | 至少两个主流服务端实现（§4.1），目标三个 |

### 1.3 明确不在范围内（非目标）

| 项 | 处置 |
|---|---|
| 服务端（inbound）实现 | 不做。Relavia 产品形态是客户端；测试台用主流服务端实现作对端（§4.1），不自研服务端凑数 |
| 老式流加密方法（`aes-*-cfb`、`chacha20`、`chacha20-ietf`、`xchacha20`、`rc4-md5`、`none`） | 统一模型中仅为无损导入而保留（schema 既有裁定）；自研模块对这些方法返回 `KindUnsupported`——与现行 sing-box 的行为一致（sing-box 1.14 已移除），**不构成回退**。弱加密警示仍由解析层按既有口径给出 |
| 插件传输（`plugin`/`pluginOpts`：obfs-local、v2ray-plugin 等，SIP003） | v1 不做。带插件字段的节点按 §3.3 规则固定走 sing-box 路径并在日志中明示原因，不许静默忽略插件字段直连 |
| SS2022 多用户/中继 PSK 链与 EIH（加密身份头） | v1 只支持**单一 PSK**。`password` 含冒号拼接的多段 PSK 时，自研模块返回 `KindUnsupported` 并由策略层回退 sing-box，不许截断或猜测语义 |
| Shadowsocks 叠加其他传输/安全层（WS/TLS 等） | 统一模型中 Shadowsocks 只有 raw 传输，不存在此组合；遇到即 `KindUnsupported` |
| TUN/路由/DNS/断网保护 | 平台层既有成果（Step 11/12）不在本文范围；自研模块只替换出站拨号，不得绕过或弱化既有路由与 kill switch 语义（§3.2 的集成约束） |

## 2. 规格基线

### 2.1 规范来源（按优先级）

1. **SIP004**（AEAD 加密与分帧）与 **SIP022**（Shadowsocks 2022 版）——shadowsocks 官方规范库（shadowsocks/shadowsocks-org）的现行文本；
2. shadowsocks 官方文档站的 AEAD / 2022 说明页（与 SIP 文本冲突时以 SIP 文本为准，并把冲突点登记到本文 §6 待核清单）；
3. 主流实现行为（shadowsocks-rust、sing-box）仅作**歧义裁决的事实参照**，不作规范来源：规范含糊处按 §4.5 的裁决规则处理并回写本文。

实施开始前，须按 §6 清单把 SIP022 的字节级细节（固定头布局、头部密钥派生、UDP 会话/包 ID 语义）逐条与规范原文核对并固化进测试向量，核对完成前不许写流式编解码代码——先向量、后实现。

### 2.2 方法（套件）口径

与现行 sing-box 适配器 `ssAEADMethods` 逐字对齐，共 7 个方法；自研模块的能力自报不得多于此集（多报即虚报），不得少报已过门禁者。

**AEAD（2017）**

| 方法 | 主密钥长 (B) | 盐长 (B) | Nonce (B) | Tag (B) | 备注 |
|---|---|---|---|---|---|
| aes-128-gcm | 16 | 16 | 12 | 16 | |
| aes-256-gcm | 32 | 32 | 12 | 16 | |
| chacha20-ietf-poly1305 | 32 | 32 | 12 | 16 | |
| xchacha20-ietf-poly1305 | 32 | 32 | 24 | 16 | |

- 主密钥：口令经 **EVP_BytesToKey**（MD5 链式展开，迭代 1 次）截取至密钥长。此处 MD5 仅是规范规定的遗留 KDF 组成，不是本项目自选的安全原语；实现用标准库 MD5 按规范组装，不许替换为其他摘要（替换即不互通）。
- 会话子密钥：`HKDF-SHA1(salt = 会话盐, IKM = 主密钥, info = "ss-subkey")`，取密钥长字节。
- 会话盐：每条 TCP 连接 / 每个 UDP 数据报独立，由 `crypto/rand` 生成，长度等于密钥长，明文置于流首/包首。
- TCP 分帧：流 = 盐 ‖ 分块序列。每块 = `AEAD(len)` ‖ `AEAD(payload)`：长度块明文为 2 字节大端长度（不含 tag），载荷块明文长度上限 **0x3FFF（16383）** 字节；nonce 为小端计数器，自 0 起，**每次 AEAD 调用**（长度块与载荷块分别计）递增。
- 首个载荷块明文以目标地址头开头：ATYP + 地址 + 2 字节大端端口；响应方向同构（响应首块为对端返回的地址头，按规范为请求目标地址的回显形态，以规范原文为准）。
- UDP：每包 = 盐 ‖ `AEAD(nonce = 0, 地址头 ‖ 数据)` ‖ tag；每包独立盐与子密钥，无分块、无计数器延续。

**Shadowsocks 2022（SIP022）**

| 方法 | PSK 长 (B) | 盐长 (B) | 底层 AEAD |
|---|---|---|---|
| 2022-blake3-aes-128-gcm | 16 | 16 | AES-128-GCM |
| 2022-blake3-aes-256-gcm | 32 | 32 | AES-256-GCM |
| 2022-blake3-chacha20-poly1305 | 32 | 32 | ChaCha20-Poly1305（IETF nonce） |

- `password` 字段为 PSK 的 **Base64 编码**（解码后长度须与方法要求一致，否则 `KindInvalidConfig`）；v1 仅单 PSK（§1.3）。
- 会话子密钥：BLAKE3 派生模式，上下文字符串固定为 `shadowsocks 2022 session subkey`，输入为 PSK ‖ 盐。
- 与 2017 版的关键差异（实现时逐条对照规范原文核实，见 §6）：TCP 采用**固定长度头 + 可变长度头**分离结构，头部由另行派生的头部密钥保护，请求头含类型字节与 Unix 时间戳，响应流使用**响应盐**（与请求盐不同，客户端必须按响应盐派生响应方向子密钥，不得复用请求盐）；UDP 每包带独立头部（含会话 ID 与包 ID，由头部密钥保护）与时间戳，服务端有防重放窗口。时间戳校验容差按 SIP022 原文取值并固化进向量（§6 待核项）。
- TCP 数据段的分块 AEAD 形态与 2017 版同构（长度块 + 载荷块），但**载荷块上限为 0xFFFF**（SIP022 §3.1.2 明文：2017 版的 0x3FFF 上限不适用于本版；2026-11-23 核对更正，见 §6 第 7 条），子密钥与 nonce 语义按 SIP022。

### 2.3 与统一节点模型的对应

| 模型字段（`spec/` 冻结 schema） | 自研模块消费方式 |
|---|---|
| `protocol = "shadowsocks"` | 路由键：命中自研模块的唯一协议 |
| `server` / `port` | 出站拨号目标（服务器端点） |
| `credential.method` | §2.2 七方法之一；表外值在 `ValidateConfig` 阶段以 `KindUnsupported`（运行面不支持）或按 schema 校验以 `KindInvalidConfig` 拒绝，两者不得混淆 |
| `credential.password` | 2017：口令原文（EVP_BytesToKey 输入）；2022：Base64 PSK |
| `credential.plugin` / `pluginOpts` | 非空即出局：该节点不进自研路径（§1.3、§3.3） |
| `udp` | false 时自研模块只提供 TCP，UDP 关联请求以 `KindUnsupported` 明示拒绝；true 时 TCP/UDP 双路 |
| `transport` / `security` | Shadowsocks 在模型中恒为 raw / 协议内建 AEAD；出现其他组合即 `KindUnsupported` |
| `source` / `group` / `lastTest` | 与内核实现无关，自研模块不消费、不改写 |

模型不新增任何「后端选择」字段：后端选择是本地运行策略，不是节点数据（§3.3），不得污染可导出的节点模型。

### 2.4 密码学库选型（实现阶段的约束，本文先定）

| 原语 | 允许的实现 | 说明 |
|---|---|---|
| AES-GCM | Go 标准库 `crypto/aes` + `crypto/cipher` | |
| ChaCha20-Poly1305 / XChaCha20-Poly1305 | `golang.org/x/crypto/chacha20poly1305` | 已审的 x/crypto 实现 |
| HKDF-SHA1 | `golang.org/x/crypto/hkdf` 或 Go 标准库 `crypto/hkdf`（以实现时 `core/go.mod` 的 Go 版本为准，二选一并在 SBOM 登记） | info 串固定 `ss-subkey` |
| MD5（仅 EVP_BytesToKey 组装） | Go 标准库 `crypto/md5` | 仅限该 KDF 内部，禁止他用 |
| BLAKE3 | 优先复用模块图中已有的成熟实现（sing-box 依赖链已带入者，实施时以 SBOM 核对为准）；无现成时引入 `lukechampine.com/blake3` 或 `zeebo/blake3` 二选一，须在 Step 2 式许可证审计口径下登记 | 派生与带密钥哈希两种模式均只许调用库函数 |
| 随机数 | `crypto/rand` | 盐、nonce 初值等一切随机量唯一来源 |

新增依赖须走既有 SBOM/许可证登记流程；本模块目标是**零新增密码学依赖**（BLAKE3 若已在图内则全表零新增）。

## 3. 接线设计

### 3.1 形态：复合适配器，协议级路由

新增一个实现 `kernel.Adapter` 的复合适配器（工作名 `selfdev`，`KernelID` 自报须与 `sing-box` 区分，如实标注为本项目自研后端），内部持有：

- **自研 Shadowsocks 引擎**：只实现 §1.2 的出站面；
- **sing-box 适配器实例**：其余全部协议，以及被策略排除出自研路径的 Shadowsocks 节点。

路由发生在 `ValidateConfig` / `Start` / `TestHandshake` 入口，按 `Config.Node.Protocol` 与 §3.3 策略决定本节点的执行后端；`Capabilities()` 返回两者并集（平台能力部分与现行 sing-box 适配器同源，不得借并集虚报平台面）。`Stop` / `Status` / `QueryTraffic` 对两个后端做聚合：流量计数为两后端之和并在内部结构中保留分后端明细供诊断（对上层仍是既有 `TrafficStats` 形态，接口签名零改动）。

上层调用方（`app/service` 的分发逻辑）今天按协议把 openvpn 分给进程适配器、其余分给 sing-box 适配器；接入复合适配器后，进程内这一路整体换为复合适配器即可，**分发逻辑与接口不变**——这是首选接法，禁止为自研模块在上层新开特殊分支。

### 3.2 集成约束（Start 路径的真实成本所在）

现行 sing-box 适配器的 `Start` 是「本地 mixed 入站 + 路由 + 出站」整箱启动。自研引擎只是一个出站拨号器，不能塞进 sing-box 箱内替换其出站。因此分两期接线，顺序不可颠倒：

- **一期（握手面）**：`TestHandshake` 的 Shadowsocks 路径改走自研引擎直拨（自研 SOCKS5 协商探针逻辑复用现行握手测试的形态：经自研出站取回探测 URL 的 HTTP 响应才算成功，口径与 Step 7 一致）。此面最小、最先过差分门。
- **二期（数据面）**：复合适配器自备本地监听与转发层：本地入站（SOCKS5/HTTP，与现行 mixed 入站等价的回环监听）→ 按当前节点后端分发：Shadowsocks 走自研引擎，其余整会话委托 sing-box 适配器。**Step 11 的路由/DNS 策略（`core/routecfg` 边车语义、远程解析 detour、fake-ip 默认关）与 Step 12 kill switch 挂点必须在转发层逐项保持**，逐项对照清单随实现交付，缺一项即二期不验收。
- TUN 模式下的数据路径（libbox/Android）同理：自研引擎只替换出站段，TUN 编排（`core/singbox` 的 tuncompile 与 Android 壳）不在替换面内；若某平台形态暂时无法把自研出站与 TUN 编排组合，该形态下 Shadowsocks 如实维持 sing-box 路径并登记，不许为赶进度绕过 TUN 编排。

### 3.3 切换、回退与默认化纪律

后端选择是**本地运行策略**，存应用本地设置（不入节点模型、不随节点导出），三档：

| 策略 | 行为 |
|---|---|
| `singbox`（初始默认） | 全部 Shadowsocks 节点走 sing-box；自研引擎仅供测试台与握手面灰度 |
| `auto`（门禁通过后的目标默认） | Shadowsocks 节点默认走自研；下列情形自动固定走 sing-box 并记录原因：节点带插件字段、多段 PSK、自研路径 `TestHandshake` 失败一次（该节点被「钉」在 sing-box 直至用户手动重置或节点数据变更）、用户手动指定 |
| `selfdev`（仅供测试/诊断） | 强制自研，失败即失败，不回退——禁止作为正式版默认 |

纪律：

- **禁止会话中途切换后端**：回退只发生在连接建立决策点（测活/启动时）。已建立的会话不迁移，避免同一连接前后字节语义不一致。
- 回退必须留痕：日志记录节点 ID、原后端、回退原因（结构化错误 Kind），UI 侧在节点详情可见「实际后端」——能力诚实原则，用户有权知道自己的流量实际走了哪套实现。
- 默认化（`auto` 成为默认）的前置条件是 §4.6 全部门禁通过 + 至少一个 Beta 版本周期的 `singbox` 默认灰度无 P0/P1 事故；回退开关在默认化之后至少保留两个正式版本（方案书 6.2 第 4 条）。
- 自研引擎 `Start` 返回 `KindInternal` 级错误时，复合适配器当次启动整体失败并如实上报，不许偷偷改走 sing-box 掩盖缺陷（测活路径的单次失败回退是上条 `auto` 策略的明示行为，与此不冲突）。

### 3.4 错误分类对齐

自研模块的一切失败必须映射到 `core/kernel` 既有 Kind 体系，不得新造分类：配置结构问题 → `KindInvalidConfig`；方法/组合不在支持面 → `KindUnsupported`；对端不可达、认证失败（AEAD 校验失败、口令错误）、响应超时 → 进 `HandshakeResult.Error` 的 `KindHandshakeFailed`（握手面）或按接口契约返回；本地拨号/DNS 引导失败 → `KindNetwork`；内部缺陷 → `KindInternal` 并视为 bug 优先处理。**AEAD 校验失败与口令错误在客户端不可区分**，两实现都只报握手失败，差分比对时按同一类处理（§4.3），禁止自研模块自创「密码错误」文案误导用户。

## 4. 差分测试计划

测试台本体（骨架、流水线）属 Step 21 交付；本节是 Shadowsocks 切片的用例与门禁设计，阈值在此**定版提议**（方案书 6.2 写「阈值在 Step 24 定版」、第 14 章 Step 21 又含「6.2 门禁阈值定版」——两处口径不一致，本文按 Step 21 先行定版、Step 24 复核时如需调整须回写本文并说明理由）。

### 4.1 对照组与互通对象

| 角色 | 实现 | 用途 |
|---|---|---|
| 对照组客户端 | sing-box v1.14.4 出站（现行适配器） | 差分基准 |
| 被测客户端 | 自研引擎 | |
| 服务端 A | shadowsocks-rust（ssserver，现行稳定版，实施时锁定版本并登记） | 互通 + 字节级参照 |
| 服务端 B | sing-box 入站 | 互通（与对照组同源，权重低于 A） |
| 服务端 C（可选） | Xray-core 入站 | 第三方互通，做了加分、缺了不扣门禁（方案书 6.2 下限是两个） |

全部测试在本机回环或受控局域网内完成，不使用任何真实第三方节点（来源治理第 7 章：测试不消费未授权节点）。

### 4.2 样本矩阵（有效集）

维度全交叉为基准集，规模失控时按「每方法至少覆盖全部维度各一次 + 高风险组合全交叉」裁剪并登记裁剪规则：

- 方法：§2.2 全部 7 个；
- 承载：TCP / UDP；
- 目标地址：IPv4 / 域名 / IPv6（含域名长度 1、63、255 边界）；
- 载荷形态：空载荷、1 B、1 KiB、恰 0x3FFF、0x3FFF+1（强制跨块）、1 MiB 流（多块）、UDP 单包上限附近的大包；
- 流形态：单请求单响应、同一连接连续多请求、半关闭（写端关闭后读响应）、并发多连接（≥32）、长连接空闲后复用；
- 口令形态：短口令、长口令（>64 B）、含非 ASCII 字节的口令、2022 的合法 Base64 PSK（含带填充/不带填充两种编码形态——以主流实现接受度为准并登记）。

流量脚本双端复用：同一脚本先驱动对照组、再驱动被测组，脚本与样本集版本化存入仓库（测试台目录），任何人可复跑。

### 4.3 比对口径（比什么、怎么比）

盐随机导致线上字节天然不同，**不做原始密文逐字节比对**（固定盐向量除外，见 §4.4）。比对四层：

1. **结果层**：握手成功/失败、端到端载荷完整性（响应体哈希）、延迟量级（不作精确比对，只作异常哨兵：被测中位延迟劣于对照组 25% 以上触发调查，不直接判负）。
2. **明文层**：在服务端侧记录解密后明文流，两组必须逐字节一致（含地址头、载荷切分语义）。
3. **结构层**：线上帧结构不变量必须一致——盐长、每块开销（长度块 2+tag、载荷块 tag）、块数与 0x3FFF 切分点、UDP 单包总开销。此层用固定盐注入钩子（仅测试构建）做确定性比对：同盐、同子密钥下两组实现产生的密文流应逐字节一致；自研组与向量集（§5 清单）的期望值比对也在此层。
4. **错误层**：异常集（§4.4）下两组的失败分类（§3.4 Kind）与失败时机（建连期/首包期/流中期）必须一致；不可区分的情形（如 AEAD 失败 vs 口令错）按同类合并后再比。

### 4.4 异常与边界集（无效集）

错误口令/错误 PSK、Base64 解码非法、PSK 长度不符、服务端中途断开、响应盐/数据被篡改 1 比特、流在盐中途/长度块中途/tag 中途截断、长度块声称超 0x3FFF 的畸形流、UDP 包截断与重复包、2022 时间戳过期/超前（时钟偏移样本）、多段 PSK 与插件字段节点（应走回退而非自研直连）、`udp=false` 时的 UDP 请求。每条样本标注期望分类与期望时机，作为 §4.3 第 4 层的判据。

### 4.5 模糊测试

- **目标面**（客户端只收响应方向与本地输入，故攻击面在此）：① 响应流解码器（TCP 分块读取 + AEAD 开封）；② UDP 响应包开封器；③ 2022 头部解析（固定头/可变头/UDP 独立头）；④ 节点配置校验入口（方法/PSK 解析）。
- **方法**：Go 原生 fuzz（`testing.F`），每个目标面一个 fuzz 目标；种子语料来自 §5 向量集的合法流 + 异常集样本；变异以比特翻转、截断、长度字段扰动为主。差分模糊（进阶项）：同一变异输入同时喂两组解码器，分类结果不一致即自动留存样本——此项列为测试台二期能力，不挡一期门禁。
- **语料来源**：仅自造与规范向量，禁止抓取真实用户流量或第三方节点流量充语料。
- **门禁量**：合并前 CI 每目标短跑 5 分钟无崩溃；发版候选每目标累计 ≥8 小时无崩溃、无挂死（超时样本按崩溃计）、无内存安全问题（Go 内存安全语言，此项主要指 panic、越界与无限循环/内存膨胀类缺陷）；新发现的崩溃样本必须先入回归集再修复。

## 5. 测试向量清单（设计）

向量文件的逐条清单见配套文件 `docs/自研协议路线-01-shadowsocks-测试向量清单.md`；向量数据文件（JSON + 二进制流）在实现阶段按清单生成并存入测试台 `testdata`，生成工具与来源逐条登记。原则：

- 确定性优先：凡密码学与分帧向量，一律固定口令、盐、nonce 初值，给出期望中间值（子密钥）与期望密文，使任何实现可离线复验，不依赖在线服务；
- 双源交叉：每条 P0 向量的期望值至少由两个独立来源核对（规范附例 / shadowsocks-rust 实测 / sing-box 实测，三者取其二），单源向量只能列 P1；
- 负向量与正向量同等地位：期望「失败」也是期望值，须标注期望失败点与分类。

## 6. 实施前待核清单（字节级，核完回写本文并勾除）

> **核对结论（2026-11-23，第一工作包第一步完成）**：以下六项已逐项核对完毕。依据来源：SIP004（shadowsocks-org `docs/doc/aead.md`，即 SIP004/SIP007 的现行文本）与 SIP022（同仓 `docs/doc/sip022.md`）原文；交叉验证：sing-shadowsocks2 v0.2.2（sing-box 1.14.4 依赖，`shadowaead_2022`）源码、shadowsocks-rust v1.25.0 实测。六项全部勾除；核对中另发现 §2.2 一处口径错误（2022 年版 TCP 载荷块上限），已在下方第 7 条更正并同步修正 §2.2。

1. ~~SIP022 TCP 固定头与可变头的逐字节布局、头部密钥的 BLAKE3 派生输入与模式（带密钥哈希/派生模式）、长度字段的保护方式~~ —— **结论：不存在独立的「头部密钥」。** TCP 请求/响应头与数据块同属一条 AEAD 流，由会话子密钥（BLAKE3 派生模式，上下文 `shadowsocks 2022 session subkey`，输入 PSK‖盐，见 §2.2）加密，nonce 为 12 字节小端计数器、自 0 起逐块递增。请求固定头明文 = 类型 1 B（0）‖ 时间戳 u64be ‖ 可变头长度 u16be，共 11 B，作第一个 AEAD 块（线上 11+16=27 B）；可变头 = ATYP‖地址‖端口‖填充长度 u16be‖填充‖初始载荷，作第二个 AEAD 块，其明文总长即固定头中的长度字段（长度字段本身在固定头块内受 AEAD 保护，无独立保护方式）。「头部密钥」概念只存在于 UDP 的 AES 方法：独立头由 **PSK 直接作密钥的 AES 分组密码**单块加密（非 BLAKE3 派生）。依据：SIP022 §2.2、§3.1.2–3.1.3、§3.2.1；sing-shadowsocks2 `SessionKey` 与 `clientConn.writeRequest/readResponse` 逐字一致。
2. ~~SIP022 时间戳校验容差的规范原文数值（请求头与 UDP 包两处是否同值）~~ —— **结论：两处同值，30 秒。** SIP022 §3.1.3 与 §3.2.3 均为「与本机时间差超过 30 秒 MUST 按重放处理」；服务端盐池保留 60 秒（§3.1.5、§3.2.4）。sing-shadowsocks2 客户端校验为 `diff > 30` 拒绝（TCP 头、UDP 包两处同式）。向量 W22-06/NEG-04 按 30 秒整定界（差 30 秒整 = 界内，31 秒 = 界外）。
3. ~~SIP022 UDP 独立头的逐字节布局、会话 ID/包 ID 的生成与递增规则、客户端侧对响应包会话 ID 的校验义务~~ —— **结论：** AES 方法独立头明文 = 客户端会话 ID 8 B ‖ 包 ID u64be，共 16 B，以 PSK 为密钥 AES 单块加密置于包首；正文 AEAD 的 nonce = 独立头明文的第 4..16 字节（会话 ID 后 4 B ‖ 包 ID），会话子密钥的「盐」= 会话 ID 的 8 B 原始字节。会话 ID 由发起方随机生成（客户端会话与服务端会话相互独立，服务端 MUST NOT 复用客户端会话 ID）；包 ID 自 0 起逐包递增（sing-shadowsocks2 客户端内部初值取 -1 后自增，即首包为 0）。正文主头（c→s）= 类型 1 B（0）‖ 时间戳 u64be ‖ 填充长度 u16be ‖ 填充 ‖ SOCKS 地址 ‖ 载荷；（s→c）= 类型 1 B（1）‖ 时间戳 ‖ **客户端会话 ID 8 B** ‖ 填充长度 ‖ 填充 ‖ SOCKS 地址 ‖ 载荷。客户端校验义务：响应正文中的客户端会话 ID 必须等于本方会话 ID（sing-shadowsocks2 报 `ErrBadClientSessionId`）；响应独立头中的服务端会话 ID 用于关联服务端会话子密钥，并按滑动窗口校验包 ID 防重放（窗口状态只在头部语义校验通过后更新）。ChaCha 方法无独立头：包 = 24 B 随机 nonce ‖ XChaCha20-Poly1305（PSK 直接作密钥）正文，正文首部为会话 ID‖包 ID（c→s 为客户端一对；s→c 为服务端一对 + 客户端会话 ID 回显），其余主头字段同 AES 形态。依据：SIP022 §3.2.1–3.2.4、§4.1；sing-shadowsocks2 `clientPacketConn.WritePacket/readPacket` 一致。
4. ~~SIP022 响应方向：响应盐长度与位置、响应头中回显请求盐的字段语义~~ —— **结论：** 响应流 = 响应盐（长度同方法盐长 16/32 B，流首明文）‖ 响应固定头块 ‖ 首载荷块 ‖ （长度块 ‖ 载荷块）*。响应固定头明文 = 类型 1 B（1）‖ 时间戳 u64be ‖ **请求盐**（16/32 B）‖ 首载荷长度 u16be（AES-128 共 27 B、AES-256 共 43 B），该块同时充当首个长度块（其后直接是载荷块，不再另发长度块）。响应方向子密钥由响应盐独立派生，不得复用请求盐。回显请求盐的语义是把响应流绑定到对应请求流，客户端 **MUST 校验**其与本连接请求盐相等（SIP022 §3.1.3；sing-shadowsocks2 报 `ErrBadRequestSalt`）。依据：SIP022 §3.1.2–3.1.3；sing-shadowsocks2 `readResponse` 一致（其实现把固定头块作整块读取、长度字段从同一块尾部取）。
5. ~~2017 版 EVP_BytesToKey 在口令为空时的规范与主流实现行为~~ —— **结论：** EVP_BytesToKey 对空口令本身有定义（MD5 链对空输入照常展开），但统一模型层已拒绝空口令：现行 sing-box 适配器在 `ValidateConfig` 以 `KindInvalidConfig` 拒绝（`checkCompileInputs`），自研模块同点拒绝、分类一致——错误分类对齐由构造保证，该情形永不进入 KDF。依据：SIP004 密钥派生节；`core/singbox/capabilities.go` `checkCompileInputs`。
6. ~~BLAKE3 实现在现行模块图中的存在性与版本（以 SBOM 为准）~~ —— **结论：在图内，§2.4 达成零新增密码学依赖。** `docs/step7-sbom-modules.txt` 第 326、398 行登记 `github.com/zeebo/blake3 v0.2.4` 与 `lukechampine.com/blake3 v1.3.0`（均为 sing-box 传递依赖）。自研模块选用 **zeebo/blake3**（其 `DeriveKey(context, material, out)` 与规范派生模式直接对应），在 `core/go.mod` 中由 indirect 提升为直接依赖（版本不变，不构成新增引入）；lukechampine 版为 sing-shadowsocks2 所用，留作交叉参照。
7. **核对中新发现的口径更正（非原清单项）**：SIP022 §3.1.2 明文规定 2022 年版 TCP 载荷块上限为 **0xFFFF**，且「2017 年版的 0x3FFF 上限不适用于本版」。本文 §2.2 原写「与 2017 版同构……0x3FFF 上限」有误，已更正：客户端发送侧可自选 ≤0xFFFF 的分块（本实现取 0x3FFF 以与对照组结构层可比），**接收侧必须接受至 0xFFFF**；结构层比对（§4.3 第 3 层）对 2022 年版按「块长 ≤0xFFFF 合法」判读，不按 0x3FFF 切分点判读。另：PSK 的 Base64 形态存在实现分歧——sing-box（Go `base64.StdEncoding`）只接受带填充，shadowsocks-rust v1.25.0 实测接受无填充；按 §4.5 裁决规则（与 shadowsocks-rust 行为一致），自研模块**两种都接受**（先 Std 后 RawStd 试解），并在差分记录中登记此为有意分歧（配置接受面差异，非握手错误分类差异，不计入 G4 分母；NEG-05 的非法 Base64/长度不符两实现仍一致拒绝）。

## 7. 工期与风险（诚实估计）

口径：单人 + AI 协作的实际节奏（含测试与文档，不含等待 CI/真机的空转）；方案书 14.3 对整个 K-1（SOCKS5/HTTP + Shadowsocks、按 2–3 人假设）估 3–6 周，本文的单人 Shadowsocks 切片估算与之不直接可比，差异主因是人力假设与二期集成面。

| 段 | 内容 | 估计 |
|---|---|---|
| S0 | §6 待核清单核对 + 向量集生成与双源交叉 | 0.5–1 周 |
| S1 | Step 21 测试台骨架（差分跑批 + fuzz 流水线）中 Shadowsocks 相关部分 | 1–2 周（与 K-1 的 SOCKS5/HTTP 切片共用骨架，成本可摊） |
| S2 | AEAD-2017 引擎（TCP+UDP）+ 一期握手面接线 | 1–2 周 |
| S3 | SS2022 引擎（TCP 头部/UDP 会话语义为难点） | 1.5–3 周 |
| S4 | 二期数据面接线（本地转发层 + Step 11/12 语义逐项保持） | 2–4 周（全程最大不确定项） |
| S5 | 门禁跑批、模糊累计时长、缺陷修复与复跑、回退演练 | 1–2 周（墙钟含机器时间） |
| **合计** | Shadowsocks 切片端到端 | **约 6–12 周**，且门禁不过只顺延不放行 |

**主要风险**（按量级）：

1. **二期集成面被低估**（最大风险）：协议引擎本身不大，难的是在不弱化路由/DNS/kill switch 语义的前提下把 sing-box 的整箱路径拆出一条等价转发层；S4 若失控，应砍范围为「握手面 + 手动模式数据面先行、TUN 形态维持 sing-box」，而不是砍语义保进度。
2. **SS2022 头部与会话细节坑**：固定头保护、响应盐、UDP 会话/包 ID 任一处理解偏差都会表现为「某些服务端能通、某些不通」的间歇性不互通，且容易误判为网络问题——对策是 §6 先行核对 + 向量先行，禁止边写边猜。
3. **UDP 行为差异**：两组实现对 UDP 包的地址头形态（域名 vs IP 回显）、大包处理、并发会话复用策略可能不同，且回环测试不易暴露，需要专门的跨实现 UDP 样本（已列入 §4.2/4.4），实网差异在 Beta 灰度期仍可能冒头——这是保留回退开关的核心理由。
4. **AEAD 细节坑**：nonce 递增粒度（按块 vs 按 AEAD 调用）、长度块的 AAD/明文形态、EVP_BytesToKey 的截断方向等，错一处即全盘不通但本地自测可能自洽——差分与向量正是为此设防，禁止以「自测通过」替代差分通过。
5. **时钟依赖**：SS2022 时间戳使「用户设备时钟错误」成为一类新的连接失败来源，错误呈现须可理解（归入握手失败并在日志给出时钟偏移提示），此为实现阶段的明确需求而非事后补丁。
6. **维护面扩大**：双后端长期并存意味着每个 Shadowsocks 相关缺陷都要先分诊「哪套实现」，文档与日志的后端标注（§3.3）必须从第一天就做，否则支持成本失控。
