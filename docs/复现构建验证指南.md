# 复现构建验证指南（第三方验证）

> 本指南供任何第三方独立验证 Relavia 的官方发布产物：证明你从
> GitHub Releases 下载到的文件，确实由本仓库对应提交的源码构建
> 而成，且确实由发行方签名。无需信任任何单方声明——每一步都可
> 以自己复算。发布流水线的设计与口径见
> docs/step15-签名与可复现构建.md；更新清单格式见
> docs/relavia-update-v1.md。

## 0. 验证分两层，按需取用

- **第一层（分钟级）**：校验下载产物的 SHA-256 与发行清单，并验
  证清单上的 Ed25519 签名。证明「你拿到的字节 = 发行方签过的
  字节」。
- **第二层（构建级）**：从源码按同提交复现构建，比对哈希。证明
  「发行方发布的字节 = 这份源码构建出的字节」。

## 1. 准备

- git、sha256sum（或等价工具）。
- Go 工具链：有效版本须为 1.25.5（各模块 go.mod 的 go 指令）；
  较新的启动器会自动切换/下载该工具链，`cd app && go version`
  显示的应为 go1.25.5。
- 第二层 Android 目标另需：JDK 17、Android SDK（platform 34 +
  build-tools）、Android NDK、Gradle 8.11.1、gogio v0.10.3、
  SagerNet gomobile/gobind v0.1.13（版本由仓库脚本锁定）。

## 2. 第一层：校验下载产物与发行签名

在 GitHub 仓库的 Releases 页面下载目标版本的文件：产物本体
（如 `relavia-windows-amd64.exe`)、`update-stable.json`（或
`update-beta.json`)、`SHA256SUMS`、`release-pubkey.txt`（发行
公钥，base64 一行）。

1. 校验和比对：

   ```
   sha256sum -c SHA256SUMS
   ```

   每个文件应报 OK。与清单无关的独立交叉核对：产物自身的
   sha256 应等于 `update-<channel>.json` 中对应 platform 条目的
   `sha256` 字段。

2. 构建发行工具（只依赖仓库源码）并验签：

   ```
   cd tools/releasetool && go build -o /tmp/releasetool .
   /tmp/releasetool verify \
       --manifest update-stable.json \
       --pubkey release-pubkey.txt \
       --dir <产物所在目录>
   ```

   预期输出每个产物一行 `signature OK, file hash OK`，末行
   `manifest OK: ...`。任一篡改（产物改一字节、清单 sha256 被
   换、签名伪造）都会以 FAIL 明示并以非零码退出。

3. 公钥真实性（带外核对）：`verify` 输出末尾会打印公钥指纹
   `SHA256:...`。把它与官网下载页公布的发行公钥指纹逐字比对
   ——不要只信随包附带的 `release-pubkey.txt`。注意：在正式发
   行密钥回填之前，客户端内嵌与演练所用的是明确标注的
   TEST-ONLY 测试钥；以官网公布的指纹为准判断你验的是哪把钥。

## 3. 第二层：从源码复现构建

1. 取与发布相同的提交：发布附带的 `RELEASE-NOTES.txt` 记录了
   `git commit`。检出该提交（或从该提交导出干净源码树）。
2. 运行仓库自带的复现检查（默认从 HEAD 导出两棵隔离目录的干
   净源码树，分别构建后比对 SHA-256):

   ```
   scripts/release/repro-check.sh windows    # Windows 客户端
   scripts/release/repro-check.sh gio        # Android Gio 逻辑 APK
   scripts/release/repro-check.sh shell      # Android 壳 APK
   scripts/release/repro-check.sh all        # 全部
   ```

   结论分三档，如实输出：`REPRODUCIBLE`（两遍逐字节一致）、
   `NOT REPRODUCIBLE`（哈希不同，并给出 zipdiff/字节差定位）、
   `UNVERIFIED (env)`（本机缺构建工具，需在具备工具的环境复
   验——CI 的 repro 作业即为此设）。
3. 把检查输出的哈希与该版本 `SHA256SUMS` 中同一产物的哈希比
   对：一致，即完成「源码 → 官方字节」的闭环证明。

各目标的前提与注意：

- **windows**：只需 Go 工具链。构建脚本强制
  `-trimpath -buildvcs=false -buildid=` 与版本盖章，路径与
  VCS 信息不进二进制。
- **shell**：Gradle 工程按设计强依赖数据面绑定
  `android/app/libs/libboxbind.aar`（缺失即构建失败，防止产出
  无数据面的壳）。该 AAR 是构建产物、不入仓库：先在检出目录
  运行 `scripts/build-android.sh bind`（需 gomobile + NDK）生
  成它，repro-check 会把同一份 AAR 作为共同输入注入两棵导出
  树——它验证的是「给定该输入，Gradle 打包可复现」；AAR 本身
  的复现性不在此检查范围内。
- **gio**：需要 NDK。 APK 的字节级复现以「签名钥相同」为前
  提：repro-check 在未注入发行钥时自动生成一次性 TEST-ONLY
  测试钥供两遍构建共用（随临时目录删除，绝不可用于真实发
  行）；核对官方已签名 APK 时，只有持有同一发行钥的构建才
  可比对哈希。

## 4. 客户端侧的自动验签（补充说明）

Relavia 客户端自身的更新机制执行同一套校验（先比 size 与
SHA-256，再以其内嵌的发行公钥验 Ed25519 签名对实际摘要成
立），篡改与回滚在客户端会被拒绝并删除下载物，错误码见
docs/relavia-update-v1.md §6。手动按本指南验证与客户端自动
验证是同一条信任链的两个入口。

## 5. 读不懂的结果时

- `BUILD FAILED` 与 `NOT REPRODUCIBLE` 是两回事：前者是构建
  本身没跑通（看同目录的 build 日志），后者才是复现性结论。
- APK 哈希不同但 zipdiff 显示仅 ZIP 元数据（时间戳等）不同、
  条目内容全同时，结论是「内容等价、容器元数据未归一」——
  按 docs/step15-签名与可复现构建.md 的分级如实记录，不要当
  作逐字节复现。
- 任何一步对不上，都欢迎在仓库开 Issue 附完整输出——这正是
  本指南存在的目的。
